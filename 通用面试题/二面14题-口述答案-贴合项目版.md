## 1. Agent 工具调用中断了怎么处理?(重试、持久化)

嗯,这个我在两个项目里分别处理过,一个管"当下这次调用",一个管"跨进程的任务"。

先说单次调用层面。MadaCode 里每个回合有一个贯穿全链路的 CancellationToken,工具调用被中断——不管是用户主动取消还是异常——我要保证会话不被破坏:已完成的、执行中的、还没开始的调用**分别回填结果**,维持 tool_use 和 tool_result 严格配对,这样中断之后可以直接续聊,不用重开会话。重试的话,要先分错误类型,超时限流这种可重试的走退避重试,参数错误这种重试没用,直接把错误作为 tool result 喂回给模型让它自己调整。

持久化层面,两个项目各有一套。MadaRag 的文件处理走 **Outbox 模式**:任务和"要发这条消息"在同一个本地事务里落表,独立调度器扫描投递,失败线性退避重试(10 秒递增封顶 5 分钟),最多 10 次进死信并把任务标失败让用户可见——所以调度器进程挂了、Kafka 挂了,任务都不会丢,状态最多是延迟收敛。MadaCode 的 Long-Running 模式则是**任务状态持久化到 task store**,进程被杀,恢复时 recover 逻辑检测到 RUNNING 状态的残留任务,触发 PROCESS_RESTARTED 把它迁到 INTERRUPT 态——防止一个死了的调度器"复活"出幽灵任务。

> 深挖预案:被问"重复执行怎么办"→ 幂等答法见第 4 题末尾;被问取消细节 → MadaCode 03 文档(volatile 读 + synchronized 写、回调锁外触发)。

## 2. 根因误判后怎么重新诊断?LangGraph 的边界跳转条件怎么设计?

这里我先如实说:**我没有用 LangGraph,我的两个项目都是自己手写的 Agent 循环**——MadaCode 是个通用 ReAct Agent,MadaRag 的问答层也是 ReAct,检索是模型可调用的工具。所以我按我自己的实现来讲"误判后重来"这件事,思路和 LangGraph 的条件边是相通的。

ReAct 循环本身就是"假设—验证"的回环:模型给出一个动作,工具执行的**真实结果**作为 tool message 回到上下文——判断错了,证据摆在那,模型下一轮基于新证据修正方向,不需要我显式写"跳回诊断节点"的边,因为上下文里已排除的假设天然留着,模型不会在同一个坑里转圈。我要做的是给这个回环**设预算**:MadaRag 的问答是硬编码 4 轮模型调用 + 8 次工具调用;超预算的处理我觉得比"报错"更讲究——**缴械收尾**:把工具列表撤空再调一次模型,它没有工具可用,只能基于已收集的证据尽力作答。用户拿到的是"尽力的答案"而不是"预算超限"。MadaCode 那边更进一步是动态预算,Long-Running 模式按任务列表规模算允许的执行周期,每轮重算,发现新问题预算自动变大。

如果非要对应 LangGraph 的概念:我的"跳转条件"就是循环里读状态做路由——有 tool_calls 继续,没有就收尾,预算耗尽走强制收尾分支;checkpointer 对应我这边的任务状态持久化。框架不同,骨架是一样的。

## 3. 为什么用定时轮询而不是 MQ 触发?

**⚠️ 原帖场景是运维告警,不是我的项目**——但这个技术选型我在 MadaRag 里真实做过,而且是**两个都用了,各管一段**,我按这个讲。

MadaRag 的文件处理链路里,MQ 和轮询是配合关系:业务事件的**传递**用 Kafka——上传完成后消费者异步做解析、切块、向量化,这段要的是实时性和削峰,MQ 合适。但"把事件可靠地送进 Kafka"这一段,我反而用的是**定时轮询**:Outbox 调度器每 5 秒扫一次到期条目再投递。为什么这段不直接发 MQ?因为 DB 写入和 Kafka 发送没有跨系统事务,直接发要么丢任务要么出幽灵消息;轮询扫表有个天然好处是**自带兜底**——这一轮投递失败,下一轮还会扫到它,失败重试不需要额外机制,是"拉"模式免费送的。

所以我的结论是:这不是二选一,**事件传递用 MQ 要实时性,可靠性兜底用轮询要不丢**。纯轮询的代价是延迟下限就是扫描间隔,纯 MQ 的代价是丢一条就永远丢了——组合起来各取所长。

## 4. 轮询任务暴涨,分批轮询对服务器的压力怎么办?

分批解决的是削峰。拿我 Outbox 调度器的实际做法说:每轮扫描**只取 top 50 条**到期条目,处理完等下一个周期——单轮工作量有上限,任务再多也是匀速消化,压力是个平稳常量而不是尖峰。任务真的暴涨、单实例追不上的时候,我这套设计天然支持**水平扩展**:多个调度器实例同时扫,靠**条件 UPDATE 抢占认领**保证一条任务只被一个实例拿到——UPDATE 返回 0 行就是被别人抢了,跳过,无锁等待;认领带 120 秒租约,抢到的实例挂了,租约到期条目自动回到可认领状态。这比 SELECT FOR UPDATE 好,因为不用持有行锁等慢操作(投递 Kafka)做完。

再往上还有两层通用手段:按 hash 把任务打散到整个周期错峰,别让一万个任务挤在同一秒;能合并的走批量接口一次拉。任务分级降频也可以做,核心任务高频、边缘任务低频。

> 顺带的幂等答法(必被追问):任务被两个实例重复处理的最坏情况要想清楚。我的场景里关键操作天然幂等——状态迁移重复标记不变、ES 写入按 fileMd5+chunkId 定位重复写是覆盖。严格说这是"天然幂等"不是"显式幂等控制",要做严格一次应该在入口按 jobId 判重,这在我的改进列表上。

## 5. 长耗时操作,ReAct 里工具是同步还是异步调?

长耗时操作绝对不能让请求线程同步等,我在 MadaRag 里两个粒度都处理过。

第一个粒度是**请求线程不阻塞**。问答的 ReAct 循环整个扔进独立线程池异步跑,WebSocket 处理线程立刻释放;线程池满了优雅拒绝——标记失败并告知用户"系统繁忙",而不是把连接吊死。循环内部还有 120 秒的 deadline 轮询,超时主动掐掉上游 LLM 流。

第二个粒度是**分钟级任务彻底异步化**,这就是原帖问的 Pod 启动那类场景。我的文件处理就是这样:上传接口把文件落对象存储、任务落库后**立即返回任务 ID**,真正的解析、切块、向量化由 Kafka 消费者后台做,前端拿任务 ID 轮询状态,处理完界面变绿,失败也能看到根因——因为死信兜底会把最底层的错误原因写回任务记录。这和"提交操作 + 查询状态"拆成两个工具给 Agent 用是同一个思想:长操作变成"发起"和"查询"两个短操作。

MadaCode 那边把这个思想推到极致:小时级任务走 Long-Running 模式,控制/执行平面分离,调度器循环起 Worker,每个 Worker 做**一件有界的工作**就汇报退出——每个周期结束是天然的中断点,进度可观测,单周期失败不毁掉整个任务。

## 6. 多模态 RAG 怎么设计?文搜图、图搜图这些。

**⚠️ 非项目经历**——我先如实说,我的 RAG 项目是纯文本知识库,多模态没做过,我按我的理解答,并且会说哪些地方和我做过的文本 RAG 是相通的。

核心是用 CLIP 这类多模态嵌入模型把文本和图像映射到同一向量空间,文搜图就是文本向量去图像向量库里做相似度检索。视频抽关键帧走图像 embedding、音轨转写走文本 embedding,按时间窗分块入库,命中后能定位到时间点——这个"分块 + 溯源定位"和我文本 RAG 里三级切分加页级溯源是同一个思想,只是切分维度从字符变成了时间。

追问的几个点:图搜图走"LLM 生成描述再文本匹配"**会漏配**,描述是有损压缩,颜色纹理构图这些视觉细节文字穷举不了,所以必须以视觉向量为主、文字描述做补充信号搞混合检索——混合检索恰好是我做熟的:我的文本 RAG 就是 KNN 语义召回加 BM25 精确匹配单请求融合,多模态无非是把"两路信号"换成了"视觉向量 + 描述文本"。不同模态向量维度分布都不一样,混一个索引会互相干扰,按模态分 collection 或 namespace 隔离,检索几路并行最后 RRF 融合,并行所以延迟不叠加。

## 7. RAG 召回率是怎么算出来的?

这个我拿自己评测框架的真实做法答,并且**我不会报一个没有出处的百分比**。

测试集构建:从知识库语料出发构造"问题—相关文档"标注对,可以人工标,也可以 LLM 基于文档生成问答对再人工抽检剔除低质量的。指标上我做的是**分层评测**:retrieval 层用标注的相关文档算 **recall@k、MRR@k、nDCG@k**,都是标准公式的程序实现——所谓召回率 85%,口径一般就是 top-k 命中标注相关文档的比例(hit rate);e2e 层评最终答案,其中**引用真实性是硬校验**——答案引的 chunk 直接和召回集程序比对,能用断言的绝不用 LLM 判;faithfulness 这种必须理解语义的才用 LLM-as-Judge,而且 judge 有人工标注的校准集定期验它和人类的一致性——裁判自己也要被考核。所有报告带版本指纹(语料 hash、数据集 hash、打分器版本、judge prompt 版本),指纹不一致的两份报告拒绝对比,变量不受控的实验不是实验。

我的真实数字口径:smoke 回归集 15 个 case,RETRIEVAL 和 ISOLATION 维度 1.0,带指纹的正式报告在仓库里。我会主动说限定:smoke 集是回归门禁不是大规模基准,全量语料加真实 embedding 的大规模评测受 API 成本限制没常态化,这是下一步。

## 8. 线上没有 LLM 标注,怎么评估效果?

线上靠间接信号加 A/B。新旧策略按流量切开,对比不需要标注的行为指标:回答采纳率、用户追问率、点踩率、会话是否在少数轮次内解决。再配两个补充:定期抽样线上真实 query 做离线的人工加 LLM 评审;收集显式的点赞点踩。A/B 看趋势,抽检看细节。

我可以补一个自己项目里相关的实践:离线评测这一侧,我给 LLM 裁判做了**校准集机制**——judge 的判定定期和人工标注比对一致性,judge 的 prompt 和输出 schema 有版本号,judge 变了历史对比自动失效。线上评估其实是同一个哲学:**不信任单一评估者,用多口径互相印证**。(线上 A/B 本身我的项目没有流量条件去做,这点如实说。)

## 9. RAG 一次请求耗时多少,token 量多少?

拿我项目的实际结构说。检索这段很快:我的混合检索是**单次 ES 请求**完成——knn 段加 query 段加 rescore 段一个请求出结果,没有两路查询的二次往返,检索本身几十毫秒量级;加上查询向量的 embedding 调用,检索链路一两百毫秒。大头在生成,秒级,看输出长度。

token 预算我是硬编码控制的:单轮 completion 上限 2000 token,整个 ReAct 问答最多 4 轮模型调用、8 次工具调用,生成整体 120 秒超时兜底。输入侧是系统提示加检索回来的 top-k 证据块,每块几百 token,输入量级在几千。成本控制上我还有一套**预留-结算**的 token 配额:请求前按估算预留额度,实际用量出来多退少补,三级预算(用户当日/全网每分钟/全网当日)任何一级不够整体回滚——为什么不事后记账?流式生成几十秒,事后记账的话并发请求都在生成中时账面是 0,全放行,实际超额十倍。预留制才是"控制"不是"统计"。体验上配流式输出,首 token 快,用户体感就可以。

## 10. 召回的文档不是最新的、或者没召回,怎么处理?

三层,我项目里各有对应的真实机制。

第一层,**从源头保证知识库不留脏数据**:我的删除链路和上传一样走 Outbox,保证 DB 记录、对象存储、向量索引三处删干净——否则会出现"文档列表里没了但还能被搜出来"的幽灵文档,权限场景下这就是安全事故。更新同理,数据面收敛了,"召回到已删旧文档"这类问题从根上消掉。

第二层,**检索不足时不硬答**。我的问答是 ReAct 结构,检索是模型可调用的工具——第一轮召回不理想,模型自己换关键词再搜一轮(轮次有预算);纯文本路径还有 minScore 阈值过滤低相关噪音。预算用尽走缴械收尾,模型基于已有证据尽力作答并说明信息不足,而不是编。再往外扩就是接联网搜索工具或主动向用户确认,思路一样:把"知识库没有"显式化,而不是让模型硬编。

第三层,**答案可验证**:我做了引用溯源,答案里的 [n] 引用映射到文件加页码,点击回跳原文——用户能看到信息出处,自己判断时效性要不要采信。

## 12. IVF 索引,nprobe 调大检索变快还是变慢?百万级怎么配?

nprobe 调大是**变慢**,不是变快。IVF 先把向量聚成 nlist 个桶,查询时只探最近的 nprobe 个桶——nprobe 越大搜的桶越多,召回越高延迟越高,这是精度换速度的旋钮。经验公式 nlist ≈ 4√N,百万级 √N 是 1000,nlist 配 4000 左右;nprobe 从 nlist 的 1%-5% 起步压测召回-延迟曲线找拐点。内存紧张上 IVF-PQ 量化,召回要求特别高换 HNSW。

我可以自然衔接到自己的项目:我用的是 **ES 8 的向量检索,底层是 HNSW**,不是 IVF,但调的是同一类旋钮——knn 请求里的 `num_candidates` 就相当于 IVF 的 nprobe,控制图上探索的候选规模。我把 k 和 num_candidates 都设成 topK×30 做扩窗召回:先宽进保语义覆盖,再用 BM25 rescore 在大窗口里重排保精确。所以"召回宽度换延迟"这个 trade-off 我是在真实系统里调过的,只是索引结构从倒排桶换成了近邻图。

## 13. 游戏里 Agent 有什么应用场景,比如 NPC?

**⚠️ 非项目经历**,按理解答,但其中几个技术点和我做过的东西直接相通。

NPC 最典型。几个和普通对话机器人不一样的点:一是**人设和记忆**,NPC 要有稳定性格,还要记得和玩家的历史交互——短期对话记忆加长期记忆检索,长期记忆本质就是一个小型 RAG,这块我熟。二是**延迟**,游戏里等三秒出话体验就崩了,常见寒暄走模板或缓存,复杂对话才走大模型。三是 **NPC 要能行动**,把游戏内行为——移动、给任务、交易——封装成工具让 Agent 调,对话驱动行为,这就是标准的 ReAct 工具调用架构,和我 MadaCode 的骨架一样,只是工具集从文件操作换成了游戏动作,而且同样需要预算控制防止 NPC 无限"思考"。四是**成本分级**,重要剧情 NPC 大模型,路人小模型。

## 14. 平时 AI Coding 用得多吗?国内用不了国外大模型 API 怎么办?

这题我答起来最有底气,因为我不只是重度使用者——**我自己实现过一个 CLI Coding Agent**,就是我简历上的 MadaCode:参照 Claude Code 的交互形态,Java 实现,ReAct 主循环、二十来个工具、并发调度、上下文压缩、子 Agent 派生这些都是自己写的。做这个项目的过程让我对 AI Coding 的理解从"怎么用"到了"它内部是怎么转的"——比如为什么 Agent 有时会反复读同一个文件、上下文什么时候该压缩、工具结果怎么影响下一步决策,这些我都是从实现者视角踩过的。

日常工作流上,脚手架、单测、重构、review 都会让 AI 先来一遍,但核心逻辑和边界条件一定自己把关——恰恰因为实现过 Agent,我很清楚它的失效模式在哪,不会盲信。API 受限的问题,实际做法就是国内模型:我的 RAG 项目生产链路就是 **DeepSeek 做生成、国内 embedding 服务做向量化**,而且我把模型配置做成了运行时可切换——provider 配置存库,后台改配置下一个请求就走新模型,不用重启。个人体感是模型间有差距,但 Agent 的工作流和提示方法是通用的,换模型不换方法。

- 第 2 题主动声明"没用 LangGraph、手写循环"反而是加分项——手写过的人对框架概念的理解比只会调框架的人深。
- 数字类(4轮/8工具/2000token/120s、×30扩窗、0.2:1.0、5s扫描/120s租约/10次死信、smoke 15 case)与两项目系列文档一致,背串了以系列文档为准。
- 配套深挖材料:MadaCode 01-11、MadaRag 00-07 系列文档。
