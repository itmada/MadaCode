# Part A · 高频大模型应用题

## A1. 幻觉怎么治理?

"我把幻觉治理分成三道关,我的 RAG 项目每道关都有真实实现。

**第一道关,让模型有据可依**:检索质量决定幻觉下限。我做混合检索保证证据召回——语义召回保覆盖、BM25 重打分保精确;检索不足时模型可以再搜一轮(ReAct 结构),预算用尽走缴械收尾,基于已有证据尽力作答并说明信息不足,而不是硬编。

**第二道关,让答案可验证**:引用溯源。检索证据按编号进 prompt,模型作答带 [n] 引用,映射持久化到文件加页码,用户点击回跳原文。有出处的答案,幻觉是可发现的;没出处的幻觉才可怕。

**第三道关,把幻觉变成可测量的指标**:我的评测框架里,**引用真实性是程序硬校验**——答案引的 chunk 必须真的在召回集里,断言级检查;**faithfulness 用 LLM-as-Judge** 判答案是否忠实于上下文,judge 本身有人工校准集防漂移。改一版 prompt 或换个模型,跑回归就知道幻觉率有没有劣化。

一句话总结:检索给证据、引用给出处、评测给度量——幻觉从'玄学'变成工程指标。"

## A2. Prompt 怎么管理和迭代?

"两个层面。**工程层面**,prompt 是代码的一部分:进版本库、随代码评审。我的评测框架把 **judge 的 prompt 版本号计入报告指纹**——prompt 变了,历史对比自动失效,因为变量不受控的对比是无效实验。这个思想同样适用于业务 prompt:每次改动跑评测回归,用指标说话而不是肉眼感觉'好像变好了'。

**结构层面**,我的系统 prompt 是分层拼装的:固定的角色与规则、动态注入的环境信息、检索证据按编号格式化进上下文。MadaCode 里工具描述本身就是 prompt 的一部分——工具 schema 写得好坏直接影响模型调用的准确率,我调过好几轮工具描述,这也算 prompt 工程。

追问'A/B 怎么做':离线先用评测集对比两版 prompt 的指标,置信了再上线灰度,口径和第 8 题线上评估一致。"

## A3. Function Calling 的原理?模型怎么"调用"工具的?

"这题我拿自己的实现答,因为 MadaCode 的整条链路是我手写的。

模型本身**不执行任何东西**,它只做一件事:根据对话上下文和你声明的工具 schema(名字、描述、JSON Schema 参数),在输出里生成结构化的 tool_use 块——本质是'以生成 JSON 的方式表达意图'。真正的执行在我的应用侧:解析 tool_use、校验参数、找到对应工具实现执行、把结果包成 tool_result 消息追加回上下文、再调一次模型。这个'生成意图→执行→结果回填'的循环就是 ReAct。

几个实现细节:**tool_use 和 tool_result 必须严格配对**,一个 tool_use 没有对应的 tool_result,下一次请求 API 直接报错——所以我的取消机制要给已发出但没执行的调用回填占位结果,这是配对约束逼出来的设计。**并行调用**:模型一次可以吐多个 tool_use,我的编排器把只读工具并发执行(虚拟线程)、写操作串行。**流式下的工具调用**:tool_use 的参数 JSON 是分片流出来的,要攒完整才能解析执行。

追问'模型为什么能学会调工具':训练时做过 function calling 的对齐,但对使用者来说关键是 schema 质量——描述模糊的工具模型就会乱传参,这是我调工具描述的实际体感。"

## A4. MCP 是什么?和 Function Calling 什么关系?

"MCP 是 Anthropic 提的开放协议,解决的是**工具生态的标准化**问题。Function calling 是'模型怎么表达调用意图',MCP 是'工具从哪来'——它定义了一套客户端-服务器协议,任何人写一个 MCP server 暴露工具,任何支持 MCP 的 Agent 都能接入,不用为每个 Agent 重复集成。

我在 MadaCode 里**实现过 MCP 客户端**:配置加载、和 server 的握手与工具发现、把 MCP server 暴露的工具适配成我内部统一的工具接口——对我的 ReAct 循环来说,MCP 工具和内置工具没有区别,一个适配器抹平了差异。所以我可以从实现者角度说:MCP 的价值就是把'工具集成'从 N×M(每个 Agent 对接每个服务)降成 N+M(各自对接协议)。

追问'和 OpenAI 的 function calling 冲突吗':不冲突,不同层。function calling 是模型 API 层的表达格式,MCP 是应用和工具源之间的传输协议——我的实现里 MCP 发现的工具最终还是以 function calling 的 schema 形式声明给模型。"

## A5. 上下文窗口有限,长对话怎么办?(上下文工程)

"MadaCode 里我实现了**上下文压缩**:对话逼近窗口上限时,把较早的轮次总结成摘要替换原文,保留最近轮次的完整细节——模型对'刚刚发生的'需要精确记忆,对'很久之前的'只需要要点。压缩是有损的,所以触发时机和保留策略都要斟酌:太早压缩浪费信息,太晚会截断。

除了压缩还有几个互补手段,我的项目里都有对应:**检索代替记忆**——知识性内容不塞上下文,放知识库按需检索,这就是 RAG 的本质;**子 Agent 隔离**——MadaCode 支持派生 Sub-Agent,把大任务的探索过程隔离在子 Agent 的独立上下文里,主上下文只收结论,探索产生的大量中间输出不污染主线;**持久化外存**——Long-Running 模式把任务状态写进 task store,Worker 每个周期从 store 重建上下文,而不是靠一条无限长的对话续命。

一句话:压缩管'对话变长',检索管'知识变多',子 Agent 管'过程变重',外存管'任务变久'。"

# Part B · Java 八股接项目

> 原则:八股题先给标准答案(证明基本功),立刻接一句"我项目里就有实例"(证明不是背的)。
> 每题给"标准答案 → 项目实例"两段式。

## B1. ZGC 了解吗?(原帖第 14 题)

**标准答案**:"ZGC 是低延迟收集器,目标是暂停时间不随堆大小增长、控制在毫秒级。核心技术是**着色指针**(在 64 位指针里借位存标记信息)加**读屏障**——对象移动可以和应用线程并发做,访问到旧地址的线程被读屏障拦下顺手自愈转发。代价是吞吐略降和读屏障开销。JDK 21 里 ZGC 支持了分代,新生代小对象的回收效率大幅提升。适用场景是大堆加低延迟敏感,比如实时服务;吞吐优先的批处理 G1 或 Parallel 反而合适。"

**接项目**:"选型上我有个实际判断:我的 RAG 服务延迟大头在 LLM 生成(秒级),GC 那几十毫秒不是瓶颈,所以我用默认 G1 没有动——**没有量化收益的调优我不做**,这本身是个工程判断。真要压检索接口的 P99(百毫秒级),ZGC 才进入考虑。"(如实、不冒充调优经验,反而显成熟。)

## B2. 虚拟线程用过吗?和平台线程什么区别?

**标准答案**:"虚拟线程是 JDK 21 的用户态线程,由 JVM 调度、挂到少量平台载体线程上跑。阻塞(IO、sleep)时 JVM 把它从载体线程卸载,载体线程去跑别的——所以'一任务一线程'的同步写法能到接近异步的吞吐,不用回调地狱。代价与限制:synchronized 块内阻塞会 pin 住载体线程(JDK 24 之前)、不适合 CPU 密集任务、没有池化必要(创建成本极低,应当用完即弃)。"

**接项目**:"MadaCode 的工具并发调度就是虚拟线程:并发段用 `newVirtualThreadPerTaskExecutor`,每个工具调用一个虚拟线程,CompletionService 按完成顺序收结果。工具调用大多是 IO 型(读文件、跑子进程、网络请求),正好是虚拟线程的甜区。有个细节可以讲:我在取消令牌上注册 `executor::shutdownNow` 的 kill-hook,并发段结束**主动注销**这个回调——不注销的话,指向已关闭 executor 的回调会在令牌上滞留到回合结束,这是资源泄漏的隐患。用 try-with-resources 管 Subscription,进出对称。"

## B3. volatile 和 synchronized 什么时候各用?

**标准答案**:"volatile 保可见性和有序性,不保复合操作的原子性;synchronized 三者全保但有互斥开销。经典组合是**读多写少时 volatile 读 + synchronized 写**:热路径读免锁,状态变更才串行化。"

**接项目**:"我的 CancellationToken 就是教科书实现:`cancelled` 标志 volatile——`isCancelled()` 是每个循环都在轮询的热路径,免锁;`cancel()` 和回调注册走 synchronized,因为'检查是否已取消+置位+取走回调列表'是复合操作。还有两个进阶细节:**回调在锁外触发**——先在锁内把回调列表快照出来再释放锁执行,因为回调是外部代码(杀进程、关 executor),持锁调外部代码是死锁配方;**触发 exactly-once**——回调列表在锁内取走即清空,二次 cancel 看到标志位直接返回。"

## B4. 线程池参数怎么配?任务堆积怎么办?

**标准答案**:"核心数按任务类型:CPU 密集 ≈ 核数,IO 密集可放大(或者直接虚拟线程);队列有界防 OOM;拒绝策略按业务选——直接抛、调用者运行(反压)、丢弃。"

**接项目**:"MadaRag 的问答循环跑在独立线程池里,**池满时优雅拒绝**:标记生成失败并通知用户'系统繁忙',而不是让请求排队到超时或把 WebSocket 线程吊死——拒绝策略是业务决策,不是技术细节。堆积的另一个思路是**把峰值摊平**:我的 Outbox 调度器每轮只取 50 条,任务再多也是匀速消化;真正的大流量靠多实例加条件 UPDATE 抢占认领水平扩展。"

## B5. 如何保证缓存与数据库/多系统间的一致性?

**标准答案**:"跨系统没有事务,思路是最终一致:本地事务+补偿、Outbox/CDC、幂等消费。"

**接项目**:"这是我项目最扎实的部分,直接讲 Outbox 五机制:同事务落表(业务表和 outbox 表一个本地事务)、定时扫描、**条件 UPDATE 抢占认领带 120 秒租约**(多实例安全+防认领者死掉后条目悬死)、线性退避重试封顶 5 分钟、10 次死信兜底并让用户可见失败根因。为什么条件 UPDATE 不用 SELECT FOR UPDATE:FOR UPDATE 持锁到事务结束,而投递 Kafka 是慢操作,锁窗口太长;条件 UPDATE 一击即中无锁等待。Redis 侧还有一个 Lua 原子性的实例:限流的 INCR 和首次 EXPIRE 必须原子,分开发的话 INCR 后进程挂了 key 永不过期,用户被永久限流——Lua 脚本一次执行,还带 TTL<0 的自愈分支。"

## B6. JWT 认证怎么做的?有什么缺陷?

**标准答案 + 接项目**:"我项目用 Spring Security + JWT:登录签发,过滤器链校验,subject 带用户身份,配合组织标签做多租户隔离。JWT 的固有缺陷要主动说:**无状态意味着无法主动吊销**——退出登录、封号,已签发的 token 在过期前依然有效。缓解方案是短有效期+refresh token,或引入 Redis 黑名单(但那就重新有状态了,是在'无状态的伸缩性'和'可吊销性'之间做权衡)。密钥管理上,签名密钥走环境变量注入,不进代码库。"
