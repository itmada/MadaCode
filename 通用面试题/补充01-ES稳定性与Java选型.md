# Part A · ES 慢查询和稳定性问题怎么处理?(原帖第 15 题)

## 一、先亮明身份再答(开场 15 秒)

> "我项目里 ES 承担两个角色:BM25 全文检索加 dense_vector 向量检索,混合查询单请求完成。慢查询和稳定性我分'怎么发现、哪里会慢、怎么兜底'三段说。"

这句话把一道八股题变成项目题——后面每个点都有你的代码背书。

## 二、怎么发现慢查询

通用手段:ES 自带 **slow log**,给索引配 `index.search.slowlog.threshold`(比如 query 超 500ms 记 warn),定位到具体 DSL;再用 **Profile API** 看这条查询的耗时分解——时间花在哪个分片、哪个阶段(query/fetch/rescore)。应用侧我在检索适配器里记了 debug 日志(命中数、最大分数),配上耗时打点就能从业务日志侧发现劣化。

## 三、我的查询里哪里会慢(核心段,全是项目细节)

对着自己的混合查询逐段分析,这是面试官最想听的:

1. **KNN 段**:`k` 和 `num_candidates` 都是 topK×30——num_candidates 控制 HNSW 图上的探索宽度,是召回换延迟的主旋钮。我为了给 BM25 rescore 留足重排窗口把它放大了 30 倍,代价就是向量检索延迟上升;如果慢查询出在这,第一刀就是降扩窗倍数,在召回和延迟之间重新找平衡。
2. **rescore 段**:`window_size` 同样是 topK×30,rescore 是对窗口内每条命中做二次打分,窗口越大越慢。好在 rescore 只作用于头部窗口而不是全量命中,这本身就是"只为头部付出精排成本"的设计。
3. **BM25 段**:中文分词我用 **ik 分词器**,而且写读不对称——**索引用 ik_max_word 细粒度切,搜索用 ik_smart 粗粒度切**。索引侧切得细保证"查什么都能命中",搜索侧切得粗避免 query 被拆成一堆碎词导致 must 匹配又慢又噪。这是中文检索的标准搭配,能主动讲出"为什么不对称"很加分。
4. **filter 不算分**:权限条件全部放 bool 的 **filter 上下文**——filter 不参与打分、可以被缓存,比放 must 里快。我的权限过滤(本人/公开/组织标签三条件)就是这么下推的,顺带还能引到 KNN 预过滤那个安全话题。
5. **向量维度**:dense_vector 2048 维、cosine——维度直接决定内存占用和距离计算成本,HNSW 图是常驻堆外内存的,百万级文档时这是容量规划的主要变量。

## 四、稳定性怎么保

1. **检索可用性不依赖单点**:embedding 服务挂了主动降级纯 BM25;整个混合查询抛异常,catch 里再试一次纯文本路径,还失败才抛检索不可用。**宁可降质量,不降可用性**。
2. **启动时的连接自愈**:我的索引初始化器对 ConnectionClosedException 做了等待重试,并把诊断信息(endpoint、认证方式)拼进错误消息——ES 没起来时给的是可行动的报错,不是裸堆栈。
3. **写入侧不冲击查询**:文档向量化和写入走 Kafka 异步消费,写入速率天然被消费速率托底,不会一次上传打爆 ES;失败有 Outbox 重试和死信,不会靠疯狂重试冲击集群。
4. **通用运维项**(没做过的如实说):生产上还应该有分片规划(单分片 30-50GB 经验值)、副本保 HA、熔断器参数、JVM 堆不超物理内存一半留给 page cache。我的项目单机部署没有实际集群运维经验,这些是我知道但没实操过的,如实区分。

> 最后一句收尾:"总结就是——发现靠 slow log 和 Profile,我自己的查询里最贵的旋钮是扩窗倍数和 rescore 窗口,稳定性靠两层降级和异步写入,集群级运维我有认知但没实战,不夸大。"

# Part B · 为什么用 Java 做大模型应用,而不是 Python?

## 一、这题的实质

面试官真正想确认的是:**你是"只会 Java 所以硬用 Java",还是"清楚两个生态的分工后做的选择"**。答案必须表现出你了解 Python 生态,而不是回避它。

## 二、口述答案(背下来)

"我先说清楚一个分界:**模型训练和数据科学,Python 生态没有替代品**,PyTorch、transformers 这些我不会假装 Java 能替代。但我做的是**应用层**——Agent 编排和 RAG 服务,这一层的本质不是调模型,是**工程**:并发调度、状态管理、可靠性、和企业已有系统的集成。这恰恰是 Java 的主场。

具体到我的项目,有几个点是 Java 给我的实际好处。第一,**并发模型**。MadaCode 的工具并发调度用的是 Java 21 虚拟线程——一个并发段起 N 个虚拟线程跑工具,CompletionService 按完成顺序收结果,配合取消令牌注册 kill-hook 一键拆除。虚拟线程让'每个工具一个线程'这种自然写法没有平台线程的成本,而 Python 这边要么受 GIL 约束要么全面 async 化,长阻塞的工具调用混合 CPU 型任务时心智负担大。第二,**类型系统和重构安全**。Agent 系统的消息流转链路很长——tool_use/tool_result 配对、多态的工具结果、状态机——强类型让这些约束在编译期就锁死,我做过几次大重构,靠类型系统兜底。第三,**企业集成**。RAG 落地大多是接进企业已有的 Java 技术栈——Spring 全家桶、Kafka、ES 客户端、JPA,MadaRag 整个就是标准 Spring Boot 工程,这个形态交付到企业环境是零摩擦的。

至于大模型这一侧,应用层对接的其实就是 HTTP API——chat completions、embedding、流式 SSE,这些 Java 处理起来没有任何劣势;真正在 Python 生态里的东西(LangChain 之类的框架)我没有用,因为**我的两个项目就是把框架该做的事亲手实现了一遍**:ReAct 循环、工具编排、上下文压缩、MCP 客户端都是手写的。所以对我来说这不是'Java 能不能做'的问题——我已经用它做出来了,而且正因为是手写,每一层的行为我都能解释。"

## 三、常见追问

**Q:LangChain/LangGraph 都不用,不怕重复造轮子吗?**
> "看目的。生产上赶交付,用成熟框架是对的。但我的目标是把 Agent 的机理吃透,框架会把最关键的东西——循环怎么转、上下文怎么管、中断怎么传播——全部藏起来。手写一遍之后我再看 LangGraph 的文档,每个概念都能对应到我自己实现里的某个类。而且 Java 生态现在也有 Spring AI、LangChain4j,真要框架化迁移成本不高,概念是通的。"

**Q:Python 你会吗?**
> (按真实水平答,示例)"会用,写脚本、跑数据处理没问题,我评测语料的处理就写过 Python 脚本。选 Java 是工程判断不是能力短板——如果入职后团队栈是 Python,语言本身不是障碍,Agent 和 RAG 的核心概念是跨语言的。"

**Q:性能上 Java 真有优势吗?瓶颈不都在 LLM 推理上?**
> "对,单次请求的延迟大头永远在模型生成,这点上 Java 和 Python 没区别。差别在**服务侧的吞吐和资源效率**:高并发下虚拟线程/线程池的调度效率、GC 可控性、单实例能扛的连接数。另外可靠性工程——我的 Outbox、条件 UPDATE 租约、Redis Lua 限流——这些和语言无关,但 Java 生态的事务、调度、持久化设施最成熟。"
