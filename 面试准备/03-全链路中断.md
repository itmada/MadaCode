> "取消是**协作式**的:每个回合创建一个 `CancellationToken`,贯穿 QueryEngine → ToolOrchestrator → ToolExecutor → 工具内部,横向还伸进阻塞资源(HTTP 请求、子进程)。消费方式有两种:**长循环轮询** `isCancelled()`,**阻塞资源注册拆除回调** `onCancel()`(比如杀子进程、断 HTTP)。用户按一次 Esc,`cancel()` 同步触发所有已注册回调;各层各自兑现取消后,统一走三类回填 + CANCELLED 终态,配对完整、会话可续聊。"

## 二、第一个必考题:为什么不用 Thread.interrupt?

**精确答案:不是"不用",是"不靠"。** token 是主传播机制,interrupt 是辅助叫醒手段,系统两个都用、分工明确。

token 解决 interrupt 做不到的三件事(类 Javadoc L19-27):

1. **一个手势要取消一堆东西**:用户按一次 Ctrl+C,要同时取消 N 个并发 Future、一个进行中的 HTTP 流式请求、一个或多个子进程。共享一个 token,比向每个线程逐一扇出 interrupt 干净得多。
2. **取消必须跨线程边界**:模型循环、虚拟线程工具批、HTTP IO 线程是**不同的载体线程**——对其中一个 interrupt,信号到不了其他线程;子进程、HTTP 请求根本不是线程,interrupt 无从谈起。
3. **interrupt 不能携带原因**:token 的 reason(如 `REASON_PERMISSION_DENIED`)驱动下游分流出不同终态和回填文案。

**但 interrupt 也真实在用**——看 `TurnExecutor.cancel()`(L133-144):

```java
token.cancel(reason);      // 先:置位 + 触发所有拆除回调
worker.interrupt();        // 后:踢醒可能阻塞的 turn 工作线程
```

worker 线程可能阻塞在没接入 token 的等待点(sleep、锁、future.get),interrupt 把它从阻塞中踢出来。**顺序必须先 token 后 interrupt**:worker 被 `InterruptedException` 惊醒后第一件事是查 `token.isCancelled()` 取原因(TurnExecutor L96-97);若 interrupt 先到,线程醒来时 token 未置位,只能记语义模糊的 "interrupted"。一句话总结:**token 负责"为什么停",interrupt 负责"别睡了"。**

## 三、类内部走读:五个并发设计点(对照源码)

### ① 状态:volatile 读 + synchronized 写(L76-82)

```java
private volatile boolean cancelled;
private volatile String reason;
private final LinkedHashMap<Long, Runnable> callbacks = new LinkedHashMap<>();
```

`isCancelled()` 是热路径(每个循环都在轮询),用 volatile 保证可见性、免加锁;状态**转换**(cancel/注册回调)才走 `synchronized(lock)`。读多写一,读免锁——教科书级的组合,面试遇到"volatile 和 synchronized 什么时候各用"直接拿这个当案例。

### ② cancel():回调在锁外触发(L125-143)

```java
synchronized (lock) {
    if (cancelled) return;          // 幂等:第一个 reason 胜出,后续 cancel 全是 no-op
    cancelled = true;
    this.reason = ...;
    toFire = new ArrayList<>(callbacks.values());
    callbacks.clear();
}
for (Runnable cb : toFire) {
    try { cb.run(); } catch (RuntimeException ignored) { }   // 锁外!且吞异常
}
```

三个细节,每个都是一道面试题:

- **为什么回调在锁外跑?** 回调是外部代码(杀进程、关 executor),持锁调用外部代码是死锁经典配方——如果回调内部又碰 token(比如注册/注销),直接锁死。先在锁内把待触发列表**快照出来**,释放锁再跑。
- **为什么吞回调异常?** 一个写错的拆除回调不能挡住后面所有清理——第 3 个回调抛异常,第 4、5 个照样要跑,否则一个 bug 变成资源泄漏放大器。
- **exactly-once 怎么保证的?** `callbacks.clear()` 在锁内完成——回调列表被取走即清空,cancel 再进来看到 `cancelled==true` 直接返回。触发只可能发生一次,且按注册顺序(LinkedHashMap 保序)。

### ③ onCancel():已取消则立即触发(L156-183)

注册时如果 token **已经**取消了,回调**当场同步执行**,返回 no-op Subscription。为什么?否则就有一个竞态窗口:取消发生在"检查 isCancelled"和"注册回调"之间,回调永远不会被触发,阻塞资源永远不会被拆除。"注册即保证必触发(除非主动注销)"——这个契约消灭了整类竞态。

### ④ Subscription 注销:LinkedHashMap 的双重理由(L79-81 注释)

回调容器选 `LinkedHashMap<Long, Runnable>` 而不是 List,注释写明了两个原因:**保持插入序**(触发顺序确定)+ **按 id O(1) 删除**(Subscription 注销)。模块 02 里并发段的 kill-hook 用完即注销,靠的就是这个。选型有据可依——"为什么用这个数据结构"是面试送分题,前提是你答得出。

### ⑤ NEVER 单例:no-op 也要防泄漏(L45-74)

`CancellationToken.never()` 给不暴露取消手势的调用路径用(测试、某些内部调用)。两个 override 都有讲究:

- `cancel()` 是 no-op——**防止误取消毒害共享单例**;
- `onCancel()` **直接丢弃回调**——因为这是进程级单例,挂上去的回调会活到 JVM 死亡,纯泄漏;
- `isCancellable()` 返回 false——模块 02 里 kill-hook 注册前先查这个,**避免注册一个永远不会触发的"假安全网"**。

"连 no-op 对象都考虑了泄漏"——面试讲到这,可信度直接拉满。

### 生命周期:为什么不需要全局注销机制?

token **每回合创建一个**,回合结束 token 不可达,注册在上面的回调随 token 一起被 GC。没有全局注册表、没有手动 unsubscribe 义务(Subscription 注销是优化,不是义务)。**用对象生命周期代替资源管理协议**——省掉的每一行注销代码都是不会出 bug 的代码。

## 四、全链路地图:一次 Esc 的旅程(把 01/02/03 缝起来)

用户按 Esc → `InterruptController` 的 ESC 监听线程捕获按键(SIGINT 也汇入同一入口)→ `TurnExecutor.cancel(turnId, reason)` → **先** `token.cancel(reason)` **后** `worker.interrupt()` → 同一瞬间发生两件事:

**推(回调,立即)**:
- 并发段的 kill-hook → `executor.shutdownNow()` 打断执行中的工具线程
- HTTP 层的拆除回调 → 中止流式请求(流读取处抛 `CancellationException`)
- Bash 工具的拆除回调 → 销毁子进程

**拉(轮询,下一个检查点)**:
- 工具内部长循环(如 Grep 遍历目录)→ `isCancelled()/throwIfCancelled()` 退出
- ToolOrchestrator 串行段 → 跳过后续调用
- QueryEngine → 循环头/压缩后/回填后的检查点命中

**收敛(不变量兑现)**:
- 三类回填:已完成保留 / 执行中填错误 / 未开始填 skipped(权限拒绝有专属文案)
- 所有 slot 非空 → tool_use/tool_result 配对完整
- `completeWithCancellation` → CANCELLED(或 PERMISSION_CANCELLED)终态落盘
- 会话转录合法 + 语义清晰 → 直接续聊

**这张图要能脱稿画出来。** 它就是简历那句"全链路中断"的"全链路"三个字。

## 五、面试官追问预案

**Q1:为什么自己造取消机制,不用 Thread.interrupt?**
参考:"不是不用,是不靠。"token 主传播(带原因、跨载体线程扇出到非线程资源、回调注册),interrupt 辅助叫醒(TurnExecutor 取消时踢醒阻塞的 worker 线程),且严格先 token 后 interrupt——保证线程醒来能读到取消原因。见第二节。

**Q2:协作式取消有个天然软肋——如果一个工具死循环且从不轮询,是不是就停不下来?**
参考:承认,这是协作式模型的固有取舍。缓解分两层:阻塞型资源(子进程、HTTP)走 kill-hook **硬拆除**,不依赖轮询;纯 CPU 循环靠约定(长循环必须轮询,内置工具都遵守)。不选 `Thread.stop` 这类硬杀是因为它会在任意指令处掐断线程、留下不一致状态——JDK 自己都废弃了。宁可接受"恶意工具停不下来"的理论风险,不接受"任何工具都可能留脏状态"的现实风险。

**Q3:cancel() 和 onCancel() 并发调用,怎么保证回调恰好执行一次、不多不漏?**
参考:所有状态转换在同一把锁内:cancel 在锁内置位+快照+清空;onCancel 在锁内判断"已取消则标记立即触发,未取消则入表"。已取消后注册的回调当场执行——消灭"检查与注册之间被取消"的竞态窗口。触发本身在锁外,防死锁。

**Q4:为什么回调异常要吞掉?吞异常不是坏味道吗?**
参考:这里的回调是**清理动作**,语义是"尽力而为的拆除"。一个失败的拆除不该阻塞其余拆除——否则单点 bug 放大成批量资源泄漏。吞异常是坏味道的场景是"吞掉业务错误装没事";这里是"清理链上隔离故障",语义完全不同。(能区分这两种场景,本身就是加分点。)

**Q5:权限拒绝为什么走取消通道,而不是单独一套机制?**
参考:用户在权限框点"拒绝并终止",意图和 Esc 本质相同——"停下这个回合"。复用取消通道,只在 reason 上区分(`REASON_PERMISSION_DENIED`),下游据 reason 产出不同终态(PERMISSION_CANCELLED,不触发红字报错)和不同回填文案(告诉模型是用户拒绝,别重试)。一条通道、按原因分流,比两套并行机制少一半状态组合。

**Q6(串联题,大概率被问):从用户按下 Esc 到可以继续聊天,完整讲一遍系统内发生了什么。**
参考:第四节那张地图,按"推(回调)→ 拉(轮询)→ 收敛(回填+终态)"三段讲。结尾落在两个不变量:配对完整(协议层,请求发得出去)+ 终态落盘(转录干净收尾)。这道题是 01+02+03 的总和,讲顺了三个模块一起防住。
