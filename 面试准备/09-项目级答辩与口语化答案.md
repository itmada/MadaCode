# 09 · 项目级答辩 + 全模块口语化答案

> 这份文档补两个缺口：一是**项目级问题**（面试从这里开始，模块文档不覆盖）；二是把各模块追问预案的书面答案转成**口语版**——面试时照书面语背会很假，口语版才是你嘴里该出来的东西。
> 用法：项目级部分（Part A）全文熟读，尤其前四题；Part B 对照各模块文档使用，书面版用来理解，口语版用来输出。

# Part A · 项目级答辩（面试的前十分钟）

## A1. "介绍一下你这个项目"（90 秒版，必背）

> "MadaCode 是我参照 Claude Code 的交互方式，用 Java 21 从零写的一个终端编程 Agent。它能自己读写文件、执行 shell、搜代码，复杂任务还能派生子 Agent 去做。整个项目没有用 LangChain 这类框架——Agent 主循环、工具编排、上下文压缩、权限控制、会话持久化、MCP 协议栈都是自己实现的，主代码大概五万五千行、五百个类。
>
> 挑三个我做得比较用心的地方说：一是主循环的**终态设计**，所有退出路径——正常完成、用户取消、权限拒绝、API 报错——统一收敛成六种终态落盘，所以任何时刻进程挂掉都能断点续聊；二是**工具并发调度**，同一轮的多个工具调用按并发安全性切段，只读的用虚拟线程并行、有副作用的串行，结果再按模型请求的原顺序回填；三是我给它配了一套**端到端评测框架**，22 个 case 在 Docker 隔离环境里跑真实工程任务，模型的 API key 通过宿主侧代理托管、不进被测容器。
>
> 您对哪一块感兴趣，我可以展开。"

**技巧**：结尾把选择权交给面试官——他挑的方向就是你准备最充分的方向之一，因为十个模块你都过了一遍。

## A2. "和 Claude Code 是什么关系？算不算抄？"

> "交互形态和核心机制是参照它的——Claude Code 没开源，我是按公开资料加上自己重度使用的体感去反推机制，然后全部自己实现。所以'参照'是行为层面的，代码层面百分之百是这个仓库里自己写的。
>
> 而且做的过程里有不少我自己的取舍，跟它不一定一样：比如子 Agent 派生深度我刻意限制成一层，因为递归的 token 成本是指数级的；上下文压缩我做成 Micro/Full 两级策略，先裁工具结果再摘要历史。对我来说这个项目最大的价值，就是把 Agent 的每一个机制亲手趟了一遍，而不是隔着框架用。"

## A3. "开发的时候用了 AI 辅助吗？"（⚠️ 最敏感题，务必按这个口径）

> "用了，而且用得很重——我觉得这是现在做工程的正常方式，这个项目本身就是个 Coding Agent，我等于一边用 AI 一边研究 AI 怎么写代码。
>
> 我的分工是：架构怎么切、每个机制的设计取舍、哪些行为是必须保证的不变量，这些是我定的；相当一部分具体编码是 AI 辅助完成的，然后我做 review、测试和返工。所以这个项目里任何一块代码您都可以问我——设计意图、调用链路、已知的缺陷我都能讲。"

**为什么这么答**：一，诚实——被追问细节时你答得上（这两周的准备就是底气），说"纯手写"反而一戳就破；二，把 AI 辅助从减分项翻转成加分项——你面的就是大模型应用岗，会用 AI 干活本身就是岗位能力。**绝对不要**支支吾吾或者撒谎说全手写。

## A4. "为什么用 Java 写 Agent？这领域不都是 Python 吗？"

> "三个原因。一是我后端就是 Java 出身，用最熟的语言能把精力集中在 Agent 机制本身；二是 Java 21 的虚拟线程正好命中 Agent 的工具并发场景——工具执行全是 IO 密集，虚拟线程按任务创建、阻塞成本极低；三是强类型在协议层特别值：tool_use/tool_result 必须严格配对这种不变量，用 Record 加编译期校验能把一大类 bug 挡在编译期。
>
> 实际做下来我的体会是：Python 生态强在模型侧——训练、推理、数据处理；但 Agent 的宿主侧本质是个系统工程问题——并发、生命周期、进程管理，这恰恰是 Java 的主场。"

## A5. "这个项目里最难的是什么？"

> "全链路取消。难在一次取消要同时打断三种完全不同的东西：进行中的流式 HTTP 请求、虚拟线程里并行跑的工具批、还有 bash 起的子进程——而且打断之后会话还必须合法，每个 tool_use 都得有配对的 tool_result，不然下一轮请求直接被 API 拒掉。
>
> 我的方案是自研一个 CancellationToken 做主传播：长循环轮询它，阻塞资源在它上面注册拆除回调；Thread.interrupt 只做辅助叫醒，而且必须先置 token 再 interrupt，保证线程醒来能读到取消原因。取消后已完成、执行中、未开始的调用三类分别回填，最后以取消终态落盘。这块细节多，您想深入我可以接着讲。"

## A6. "如果重来一遍，你会改什么？"（拿你自己发现的缺陷答，含金量最高）

> "两个点。第一，子 Agent 失败时中间成果全丢——它跑了 29 轮、读了几十个文件，第 30 轮触顶，父 Agent 只拿到一句'超出最大轮次'，唯一合理的反应是重跑一遍、再烧一遍 token。我会给 TurnResult 加一个 partialWork 字段，失败时带回末几轮的活动摘要，不破坏隔离但父模型有东西可续。
>
> 第二，评测框架建晚了。eval 是项目后期才建的，前期改 prompt、改压缩策略全靠手感，有些回归问题发现得很迟。重来的话我会像写测试一样，机制做到一半就开始建 case。"

## A7. "项目有什么量化成果？"（诚实红线）

> "代码规模是主代码五万五千行左右、五百个类、二十个内置工具；评测框架有 22 个 case，其中 17 个是真实工程任务。通过率这类数字我不随口报——框架完整可跑，但受 API 成本限制，常态化跑的是框架自检集，真实模型的全量跑分我还没有可引用的数据，这个我如实说。"

**宁可少一个数字，不要编一个数字。**"我不随口报数字"这句话本身就是加分项。

# Part B · 各模块追问的口语化答案

> 编号对应各模块文档里的 Q。书面版负责"理解透"，这里负责"说得出"。

## 模块 01 · 主循环

**Q1 为什么不用 LangChain？**
> "主要是控制粒度。我需要的几个能力——流式输出到一半取消还要保住消息配对、回合里动态刷新工具列表、工具能反向把控制权交还运行时——框架里要么没有，要么得跟它的抽象打架。而且主循环本身就一百多行，自己写比跟框架搏斗便宜，出了问题每一行都是我能解释的。"

**Q2 流式断了会话会怎样？**
> "不会脏。流式消息的生命周期归 AssistantTurnWriter 管，它是 try-with-resources 的——成功才 commit，任何异常路径都 abandon，把半条消息整个扔掉。就算哪条路径漏写了，close 兜底默认也是丢弃、绝不静默提交。所以永远不会出现两条连续的 assistant 消息把下一轮请求搞成 400。"

**Q3 压缩失败为什么还继续发请求？**
> "因为超软阈值不等于超硬上限，那次请求很可能还是能成的。我要是压缩一失败就终止，等于把'可能没事'变成'必然失败'。真超限了 provider 会拒绝，回合以干净的 API error 结束，也不会自动重试，行为是确定的。"

**Q4 取消检查为什么散在好几个地方？**
> "取消的响应速度取决于检查密度，原则是每个耗时操作之后必查。比如压缩要调模型做摘要、可能好几秒，压缩完必须再查一次，不然用户按了 Esc 还要干等一次模型请求。还有个细节：API 异常里要先查取消再分类错误，因为按 Esc 经常表现成连接中断异常，不先查会把用户取消误报成 API 错误。"

**Q5 tool_result 为什么放 user 消息里？**
> "Anthropic 协议规定的——tool_result 块必须在 user 角色消息里，跟 assistant 里的 tool_use 按 id 配对。这也是为什么我的中断和压缩都要小心维护配对，配对一破，API 直接 400。"

**Q6 模型一直调工具停不下来怎么办？**
> "两层保险：maxIterations 保险丝，到顶写条警告、以 MAX_ITERATIONS 终态结束；再就是用户随时能取消，取消令牌贯穿全链路。"

**Q7 断点恢复怎么实现的？**
> "会话就是事实源。每条消息包括终态都追加写进 JSONL，所有退出路径都保证配对完整加终态落盘，恢复就是重放文件，不需要任何修复逻辑。断点恢复其实是终态设计的副产品，不是单独开发的功能。"

**Q8 你觉得这段最该重构的是什么？**
> "runTurn 里异常分类的嵌套比较深，可以抽成策略。另外 ToolExecutor 每回合 new 一次，跟我 DI 容器'显式装配'的理念有点出入，值得讨论要不要提成回合工厂。"

## 模块 02 · 工具并发调度

**Q1 [读A,写B,读C] 怎么执行？**
> "切三段、全串行，因为每段长度都是 1。只有连续的多个并发安全调用才并行，比如 [读A,读C,写B] 就是前两个并行、写串行。段间顺序严格保留、不做全局重排——模型可能依赖请求顺序的语义，比如先写后读。"

**Q2 并行怎么保证结果顺序？**
> "结果列表预分配，每个任务提交时捕获自己的下标，做完 set 回自己那个坑。取的时候按完成先后取，放的时候永远放回原位——执行乱序，回填有序。"

**Q3 并行跑一半取消了？**
> "三类分开处理：已完成的保留真实结果；执行中的被 shutdownNow 打断、slot 填错误结果；没开始的统一填 skipped。所有 slot 都非空，配对完整，会话照样续聊。"

**Q4 为什么虚拟线程？**
> "工具执行几乎全是 IO 密集，批量小、生命周期短。虚拟线程按任务创建、阻塞便宜，一行代码管完生命周期。平台线程池那些容量、队列、拒绝策略，在这个场景全是不需要回答的问题。"

**Q5 模型请求了不存在的工具？**
> "返回一个工具级的错误结果，模型下一轮自己改名重试。关键是不能发回合终止信号——错误分两层，工具级的可恢复错误归执行器管，回合级的终止归引擎管，混了会把同批其他工具误杀。"

**Q6 权限拒绝后同批后面的工具怎么办？**
> "权限拒绝触发取消，后面的统一回填'上一个权限请求被拒、跳过执行'。文案是特意区分的——让模型知道是用户拒绝而不是系统故障，别原样重试。"

**Q7 最坏情况并行度多少？**
> "读写交替时全退化成串行——但这是正确性要求的下界，不是缺陷。真实负载里模型倾向一次批量读多个文件，并行收益就在这些场景，没必要为最坏情况优化。"

## 模块 03 · 全链路中断

**Q1 为什么不用 Thread.interrupt？**
> "不是不用，是不靠它传播。token 负责'为什么停'——能带取消原因，能扇出到 HTTP 请求、子进程这些根本不是线程的东西；interrupt 只做辅助叫醒，把阻塞的工作线程踢醒。顺序一定是先 token 后 interrupt，这样线程醒来第一时间能读到原因。"

**Q2 有锁了为什么还要 volatile？**
> "读多写少。isCancelled 是热路径、每个循环都在轮询，volatile 保证可见性就够了，不用陪着加锁；真正的状态转换——置位、注册回调——才走 synchronized 保证原子。"

**Q3 回调为什么锁外执行、还吞异常？**
> "回调是外部代码——杀进程、关线程池，持锁调外部代码是死锁的经典配方，所以锁内只做快照和清空，锁外逐个执行。吞异常是因为这是清理链，一个坏回调不能挡住后面的清理，不然单点 bug 变成批量资源泄漏。"

**Q4 吞异常不是坏味道吗？**
> "吞业务异常是坏味道，这里吞的是清理动作的异常——语义是'尽力而为的拆除'，故障要隔离。这两种场景得分开看。"

**Q5 权限拒绝为什么走取消通道？**
> "用户点'拒绝并终止'跟按 Esc 本质是同一个意图——停下这个回合。复用一条通道、在 reason 上区分，下游按 reason 分流出不同终态和文案。比维护两套机制少一半状态组合。"

**Q6 从按下 Esc 到能继续聊，全程说一遍。**
> "分四段。入口：ESC 监听线程捕获按键，调 TurnExecutor.cancel，先置 token 再 interrupt 工作线程——顺序是刻意的，保证线程醒来能读到原因。推：token 的回调同步触发，杀工具线程池、断流式请求、销毁子进程。拉：各轮询点在下一次检查时看到标志——工具内部长循环、串行段、主循环的几个检查点。收敛：三类回填保证每个 tool_use 都有配对结果，回合以取消终态落盘。所以续聊有两层保证：协议上转录合法、请求发得出去；语义上模型知道刚才发生了什么，不会乱决策。"

## 模块 04 · 上下文压缩

**Q1 上下文溢出怎么办？**
> "分级降级。一个软阈值，170k，超了先跑 Micro——纯 CPU，把超过四千字符的历史工具结果裁掉中间、留头四分之三尾四分之一；还超再跑 Full——调小模型把早期对话做一次整体摘要，只保留最近几轮原文。切点必须选'不含 tool_result 的真实用户消息'，保证配对不被拆断。"

**Q2 Micro 和 Full 各解决什么？**
> "Micro 解决工具结果太胖——agent 读文件、跑命令的输出动辄几千行，裁它信息损失最小、毫秒级完成；Full 解决对话总量太长——有损摘要、要调模型、秒级。先便宜后贵，Micro 压够了就不动 Full。"

**Q3 切点为什么必须是不含 tool_result 的 USER 消息？**
> "切点两边，一边被摘要替换、一边保留。要是切在带 tool_result 的消息上，它对应的 tool_use 就被摘掉了，保留段里出现一个没有前驱的 tool_result，下一轮请求直接 400。真实用户消息前面一定是文本收尾的，从这切配对必然完整。"

**Q4 找不到足够的真实用户消息怎么办？**
> "降级——保留轮数从 3 降到 2 降到 1。这解决的是工具密集会话永远压不了的问题：agent 连着调几十个工具时真实用户消息很稀少，宁可少保留几轮也要完成压缩，不然会话只会涨到撞 API 的墙。"

**Q5 压缩失败为什么不终止？**
> 同 01-Q3，口径一致："超软不等于超硬,继续发,真超了 provider 拒绝、干净退出。"

**Q6 是 Map-Reduce 摘要吗？**
> "不是，单次整体摘要，就调一次模型。超大输入由上游的字符截断兜底，不靠分片归并。"

**Q7 为什么 Micro 用字符数、Full 用 token 数？**
> "Micro 在裁字符串，字符就是它的操作单位，算精确 token 没必要；Full 要判断整体有没有降到软限以下，必须用 token 估算，单位就得统一。"

## 模块 05 · Sub-Agent

**Q1 子 Agent 挂了父怎么知道？**
> "子的 Error 事件被转发器拦掉，不上冒——失败会转成一个失败的 ToolResult 回给父模型。父模型下一轮看到'子 Agent 超轮次失败'，自己决定重试还是换方案。父回合不受影响，控制权一直在父模型手里。"

**Q2 子 Agent 能越权吗？**
> "不能，三道防线：权限门是共享的同一个实例，危险操作照样弹框给用户；permissionMode 严格从父继承，不能变宽；工具集还能再用白名单收窄。安全只往下收、不往上放。"

**Q3 父为什么看不到子的推理过程？**
> "刻意设计的。父模型看到子的内部对话只会被污染和干扰，用户也只需要知道'子 Agent 在干活'——转发器只放行 token 用量和一行活动摘要。隔离是信息架构的边界，不是偷懒。"

**Q4 token 为什么上冒、消息为什么不上冒？**
> "token 上冒是计费正确性——子消耗的量不上报，账就少算了；消息不上冒是上下文隔离——上冒就挤爆父的窗口。判断标准就一条：这个信息对父层有没有语义价值。"

**Q5 子 Agent 要审批时弹框在哪？**
> "用户的同一个终端，因为 gate 是共享的。子 Agent 绕不过审批，用户也不会看到第二个窗口。"

**（追问：支持递归吗？）**
> "机制上是自然支持的——子引擎里就有 AgentTool，转发器也支持逐级冒泡；但深度上限我刻意设成 1。一是递归的 token 成本指数级，二层就可能失控；二是深层活动摘要冒到根卡片，用户分不清谁在干什么。机制留全、策略先收紧，想放开改一个构造参数就行。"

## 模块 06 · Long-Running

**Q1 控制/执行平面分离是什么意思？**
> "控制 session 存用户对话和任务规划，长期活着；执行层每个 Worker 是独立 session，干一件有界的事、汇报、然后扔掉。不分离的话，几十个 Worker 周期的对话堆在一个 session 里，上下文很快爆掉；而且一个是决策者一个是干活的，职责也不该混。"

**Q2 动态预算是怎么算的？**
> "min(硬上限, max(1, feature 数 + issue 数))——任务列表越长，允许的 Worker 周期越多。而且这个公式是在循环里每轮重算的，不是开跑前算一次：Worker 第三周期发现俩新 issue，第四周期开始前预算就变大了。这才叫动态。"

**Q3 进程被 kill 了数据丢吗？**
> "不丢。task store 是文件持久化的，每个 Worker 周期结束都写进度。重启后恢复逻辑有个强不变量——没有任何路径能让会话停在 RUNNING：孤儿任务通过租约判定后迁到 INTERRUPT，连恢复本身出异常都兜底到 INTERRUPT。死 launcher 不可能复活。"

**Q3.5 一个 issue 反复修不好会卡死任务吗？**
> "不会，这是次数乘严重级别的二维决策。没到三次就重试；到了三次，普通 issue 自动挂起、任务继续干别的，只有 blocker 级别才升级给用户。普通问题不该阻塞整体进度，blocker 顾名思义绕不过去。"

**Q4 Worker 崩了没汇报怎么办？**
> "Launcher 捕获异常，区分是被中断还是真崩了。真崩了就记事件、把任务置为 INTERRUPT、返回 FAILED——影响只有这一个周期，用户看事件日志决定要不要恢复。"

**Q5 为什么 Launcher 不是工具？**
> "调度权不能交给模型——模型能调的工具就能被模型无限调用，成本和安全都兜不住。所以设计了 YIELD_TO_RUNTIME：模型说'我要开始长期任务'，工具把控制权还给运行时，之后的调度是纯系统级循环，模型只在每个 Worker 内部干活。"

## 模块 07 · Eval

**Q1 怎么知道改动没让 Agent 变差？**
> "跑评测回归。22 个 case，每个起真实 agent 管线跑完整任务，然后评分器管线判分。判分三维正交：环境故障单列不算模型的错，执行状态和验收结果分开看。模型是非确定的，所以支持一个 case 跑多次算 pass@k，把能力问题和运气问题分开。"

**Q2 模型在评测里作弊怎么办？**
> "专门有 antihack 的 case 测这个。验收脚本在宿主侧执行、容器内不可写，模型改不了判分逻辑；SafetyScorer 还会审计危险行为和出网记录。"

**Q3 为什么用 Docker？**
> "被测的是模型生成的任意代码，必须假设它可能删库、扫文件系统、外发数据。所以三件套：文件系统隔离、网络隔离、凭证托管——API key 放在宿主侧的代理 sidecar 里，容器只拿到代理地址，请求过代理时才注入密钥，容器从头到尾摸不到 key。"

**Q4 pass@k 的 k 怎么选？**
> "成本和方差的权衡。k=1 便宜但高方差，k=5 稳但五倍成本。日常回归用低 k，重要变更前用高 k。"

## 模块 08 · MCP

**Q1 MCP 是什么，为什么不直接接 HTTP API？**
> "MCP 是 Anthropic 推的开放协议，统一模型宿主和工具方的接口。自己接 HTTP 的话，每个工具一套认证、一套 schema，N 个宿主乘 M 个工具就是 N×M 的适配量；MCP 把它变成 N+M。stdio 传输还有个好处——server 就是个本地子进程，零网络配置，权限继承宿主。"

**Q2 为什么自己实现不用 SDK？**
> "一是想真正吃透协议——JSON-RPC 加三步握手，不复杂，整个实现五百行左右；二是我要把 MCP 工具无缝塞进自己的 Tool 接口、权限门和并发调度，官方 SDK 的抽象未必贴合；三是不想为这点事引一个大依赖。"

**Q3 MCP server 崩了，等待中的调用怎么办？**
> "reader 线程发现流断了，把所有挂起的 future 全部异常完成——等待方立刻收到异常，转成工具级失败结果回给模型。加上 30 秒请求超时兜底，不存在无限挂起的路径。"

**Q4 外部工具怎么受权限管控？**
> "适配器实现的是跟内置工具完全相同的 Tool 接口，注册进同一个注册表。执行时走同样的七道关卡——权限门照过、要审批照弹框。并发安全性保守按不安全处理、一律串行，因为我不知道远端工具有没有副作用。"

**Q5 响应乱序怎么处理？**
> "每个请求分配自增 id，挂一个 future 到 pending 表里；reader 线程逐行读响应，按 id 从表里取出对应 future 完成它。哪个先回完成哪个，各调用方阻塞在各自的 future 上，互不干扰。"

## 模块 10 · Memory

**Q1 为什么分四类不用一个大文件？**
> "四类的使用时机不同——user 和 feedback 几乎每次对话都相关，project 只在做相关任务时相关，reference 只在找信息时相关。分类让模型按需取；一个大文件会膨胀成每次都得全文加载的上下文炸弹。"

**Q2 为什么不用向量库？**
> "规模不匹配。个人 Agent 的记忆是几十条量级，模型看着索引自己挑就行了，不需要语义检索。而且 Markdown 文件用户能直接打开改，透明可控。向量库适合万条级加模糊查询，这里是杀鸡用牛刀。"

**Q3 记忆错了怎么办？**
> "保存工具支持覆盖写，索引按文件名替换，模型发现记忆跟现实冲突就更新。而且文件系统天然给了用户最终否决权——直接删文件就行。"

## 使用建议

1. **A1、A2、A3 三题必须练到脱口而出**——它们出现在每一场面试的前五分钟，而且 A3 答砸了后面全白搭。
2. 口语版不是逐字背诵稿，是**语流模板**——记结构和关键词，用自己的话说。判断标准：说的时候像在聊天，不像在朗诵。
3. 每个口语答案结尾都可以加一句"这块细节挺多的，您想深入我可以展开"——把追问引向你准备好的深水区。
