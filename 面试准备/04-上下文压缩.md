# 模块 04 · 上下文压缩

> 源码位置:`services/compact/`（549 行总计，四个核心类）
> 对应简历 bullet："超阈值后分级降级，先裁剪历史工具结果、再摘要早期对话，压缩切点自动避开工具调用配对"
> 前置：01-03 已通关。本模块是 Agent 面试出现频率最高的通用主题，你有具体实现能回答，别人只能背概念。

---

## 一、30 秒电梯陈述（背下来）

> "Agent 长时间运行后会话会超出模型的上下文窗口。我用**分级降级**解决：只有一个显式软阈值（200k × 0.85 = 170k token），超过才触发压缩。第一级是 **Micro**——纯 CPU，把历史 tool_result 超过 4000 字符的部分裁掉头尾之外的中间段，保持消息数不变；如果 Micro 之后还超阈值，第二级是 **Full**——调小模型把早期对话渲染成文本做一次整体摘要，用一条摘要消息替换掉早期那段。切点选取是难点：从尾部往前找第 K 个'真实用户消息'（不含 tool_result 的 USER 消息）作为分界，保证 tool_use/tool_result 配对永远不被拆断。压缩失败不终止回合——超软阈值不代表超硬上限，provider 拒了才是硬上限，回合以 API_ERROR 干净退出。"

---

## 二、类地图

```
CompactBudget          ← 阈值配置（唯一显式软限：200k × 0.85）
CompactPlanner         ← 调度器：决定何时压缩、按序尝试策略
 ├─ MicroCompactStrategy  ← 第一级：裁剪超长 tool_result，纯 CPU，毫秒级
 └─ FullCompactStrategy   ← 第二级：整体摘要早期对话，需调模型 API
TokenEstimator         ← token 数估算（用于判断是否超阈）
```

装配在 `EngineAssembly.createCompaction()`：`List.of(new MicroCompactStrategy, new FullCompactStrategy)`——顺序硬编码，Micro 永远先于 Full。

## 三、阈值设计：只有一个显式软限（必须答准）

```java
// CompactBudget.defaults()
new CompactBudget(200_000, 0.85, keepRecentRounds=3, microMaxResultChars=4_000)
// softLimit() = 200_000 × 0.85 = 170_000 token
```

**只有软阈值，没有"硬阈值"常量。** 硬限是隐式的——超过 provider 的实际上下文窗口时，API 请求会被拒绝，回合以 API_ERROR 干净退出。`QueryEngine` 里有一段注释明说了这个设计：超软阈值不一定超硬上限，压缩失败就继续发请求，如果真超了，provider 拒绝，回合退出——没有 doomed retry loop。

**面试红线**：简历旧版写了"软/硬双阈值"——现在你知道那是不准确的，绝对不要在面试里说两个阈值。标准说法："一个显式软阈值触发压缩，超出 provider 实际上下文窗口时 API 拒绝，那是隐式硬限。"

## 四、Micro 策略走读（MicroCompactStrategy，109 行）

**做什么**：遍历所有消息，只对 `ToolResultBlock` 动手；超过 `microMaxResultChars`（4000 字符）的 tool_result，保留头 3/4、尾 1/4，中间插入 `[... N chars truncated ...]` 标记。其他类型消息（文本、思考、tool_use）**原封不动**。

```java
// 核心逻辑（L75-92）
int available = Math.max(0, maxChars - TRUNCATION_MARKER_BUDGET);  // 50字符给标记留位
int head = available * 3 / 4;
int tail = available / 4;
```

**三个面试可讲的点**：

1. **为什么只动 tool_result？** tool_result 是 agent 运行中体积增长最快的部分——读文件、bash 输出、搜索结果动辄几千行。用户的对话文本和模型的推理文本通常不大，动它们的信息损失也更高。Micro 只截最胖的那块，对话质量几乎无损。

2. **头 3/4 尾 1/4 不是随意的**：结果的开头往往是最关键的（命令输出的第一屏、文件的前几行），结尾往往是最新状态（错误信息往往在末尾），中间常常是重复的日志流。3:1 是"保头保尾"的经验比例。

3. **CancellationToken 被注释说故意忽略**（L36）：Micro 是纯 CPU 操作，耗时毫秒级，查取消只是额外开销，没有意义。这个"故意不查"是明确的设计决定，不是漏写。面试讲到这能展示你读过注释。

## 五、Full 策略走读（FullCompactStrategy，202 行）

**做什么**：把早期对话（split 点之前）渲染成文本，调小模型做一次整体摘要，用一条 `[CompactBoundary]` 用户消息替换那段，后面的对话（split 点之后，即最近 K 轮）原样保留。

**这不是 Map-Reduce，是单次整体摘要**——面试简历旧版写了"Map-Reduce"，这是不准确的。只有一次 `apiClient.send()`。

### 切点算法：这是本模块的皇冠（L141-155）

```java
int findSplitPoint(List<Message> messages, int keepRounds, int compactStart) {
    for (int rounds = Math.max(1, keepRounds); rounds >= 1; rounds--) {
        // 从尾部往前，找第 rounds 个"真实用户消息"
        // 真实用户消息 = role==USER 且不含 ToolResultBlock
        for (int i = messages.size() - 1; i >= compactStart; i--) {
            if (m.role() == USER && !hasToolResult(m)) {
                if (++found == rounds) return i;
            }
        }
    }
    return 0;
}
```

**为什么不能随便找一个切点？** 如果切在 tool_use 和其对应的 tool_result 之间，会话转录就出现了没有 tool_result 配对的 tool_use——下一次 API 请求直接 400。所以切点只能是"不含 tool_result 的 USER 消息"，因为这类消息前面的那条消息必然是以 assistant 文本（不是 tool_use）结束的——配对完整。

**降级逻辑**（面试高光）：如果找不到 `keepRounds`（默认 3）个真实用户消息，不是直接放弃，而是降到 `keepRounds-1`，再降到 1——宁可少保留几轮，也不放弃压缩。原因：深度工具循环的会话（agent 连续调用数十次工具）里，真实用户消息稀少；如果找不到 K 个就失败，这种会话永远压缩不了，上下文只会无限增长直到 API 拒绝。**保少留比完全不压缩更好。**

### 渲染 + 摘要（L69-106）

被压缩的消息先 `renderForCompact` 渲染成带角色标签的文本（`[USER]\n...\n[ASSISTANT]\n...`），如果渲染结果超过 60000 字符，还要**再做一次头尾截取**才送入摘要请求——这是嵌套的截断逻辑，防止摘要请求本身就超出 API 限制。

摘要之后重建消息列表：`[系统初始消息] + [CompactBoundary 摘要消息] + [最近 K 轮原始消息]`。

**两处取消检查**：摘要 API 调用前后各一次 `throwIfCancelled()`（L82, L94）——因为这是 Full 策略唯一的耗时操作，压缩期间用户可能按 Esc。

## 六、CompactPlanner：策略调度与 fail-open（L35-102）

```java
// planAndApply 的核心循环
for (CompactStrategy strategy : strategies) {  // [Micro, Full]
    result = strategy.apply(...);
    if (result.isPresent()) {
        emitCompacted(...);
        if (!budget.isOverSoft(estimate)) return true;  // 降到软限以下，停止
    }
}
// 所有策略都用完还超限：发 CompactFailed，继续执行回合
```

**两个关键决策**：

1. **策略链是"够了就停"**：Micro 压完如果已经低于软阈值，不会再跑 Full。Full 更贵（要调模型），能省就省。

2. **fail-open**：所有策略都用完还超软限时，发一个 `CompactFailed` 事件然后**继续执行回合**，不终止。这和 QueryEngine 里的注释呼应：超软不一定超硬，继续发请求；如果真超了，provider 拒绝，回合以 API_ERROR 退出——行为是确定的、可预期的。

压缩完成后会往会话里插一条 system 消息（L106-110）：`[compact] 250k → 120k via micro (15 summarized, 30 kept)`——这既是给用户看的状态记录，也是让模型在转录里能察觉到"这里发生过压缩"。

## 七、面试官追问预案

**Q1：Agent 上下文溢出了你怎么办？** ← 这是本模块的开门题，见电梯陈述。

**Q2：为什么分两级策略，Micro 和 Full 各解决什么问题？**
参考：Micro 解决"最近的 tool_result 太胖"——无损信息地裁中间段，毫秒级不阻塞；Full 解决"对话总量太长"——有损地摘要早期历史，但需调模型、秒级耗时。先 Micro 可以避免大多数需要 Full 的场景，保住性能和信息完整性；只有 Micro 不够时才动用 Full。

**Q3：切点为什么不能随便选一个 USER 消息，非得是"不含 tool_result 的"？**
参考：tool_use 和 tool_result 必须严格配对——如果切在 tool_result 之前，则 tool_use 留在被摘要段、tool_result 留在保留段，配对残缺，下一轮请求 400。只在"真实用户消息"处切，保证该消息之前的 assistant 消息以文本（非 tool_use）结束，配对必然完整。

**Q4：如果整个会话里只有工具调用，没有真实用户消息，Full 策略怎么办？**
参考：`findSplitPoint` 从 keepRounds=3 降到 1，再找不到返回 0，`apply` 方法看到 `split <= compactStart` 返回 empty——Full 策略放弃，CompactPlanner 报 CompactFailed，回合 fail-open 继续。这是一个极端场景，真实的会话里即使工具密集，开头也必然有至少一条用户消息。

**Q5（必考）：压缩失败了，系统为什么不直接报错终止，而是继续发请求？**
参考：见第三节和 QueryEngine 注释的逻辑——超软阈值 ≠ 超硬上限，很多时候请求仍然成功；如果真超了，provider 返回错误，回合以 API_ERROR 干净退出，用户看到明确错误。反过来，压缩失败就终止，是把一个"可能没事"的请求变成"必然失败"，对用户体验更差。fail-open 是合理的取舍，且退出行为是确定的。

**Q6：Full 策略的摘要是 Map-Reduce 吗？**
参考：不是，是单次整体摘要——早期消息渲染成一段文本，一次 `apiClient.send()` 调摘要模型。Map-Reduce 分片归并的好处（处理超大输入）由上面那层截断（60000 字符限制 + 头尾截取）来兜，而不是靠多次模型调用。

**Q7：Micro 处理的是字符数，Full 处理的是 token 数——为什么两个单位不统一？**
参考：Micro 在裁字符（截字符串），字符数天然就是操作单位；估算 token 数有额外计算成本，而 Micro 的目标只是把 result 控制在"不太大"，精确 token 数不必要。CompactBudget 的 `microMaxResultChars`（4000 字符）是经验阈值，约对应几百 token，足够实用。Full 的目标是把整体估算值降到软阈值以下，必须用 token 数判断，单位必须统一。
