## 一、30 秒电梯陈述(背下来)

> "模型一轮可能同时请求多个工具调用。`ToolOrchestrator` 把它们**按并发安全性切成连续段**:并发安全段(通常是只读工具)用**虚拟线程**并行执行,不安全段(写文件、执行 Shell)严格串行。无论怎么执行,结果都**按 slot 索引回填**到一个预分配的列表里,保证顺序与模型请求一致。每个工具调用在 `ToolExecutor` 里要过一条**七道关卡的管线**——取消检查、工具解析、访问边界、Hook、Schema 校验、Plan 模式门、权限门——全过了才真正执行。任何一关失败都产出一个**per-tool 的失败结果**,不会终止整个回合,模型看到错误信息后可以自行纠正重试。"

## 二、切段算法:三行核心代码(ToolOrchestrator L92-97)

```java
while (i < toolCalls.size()) {
    int segmentStart = i;
    boolean safe = isConcurrencySafe(resolvedCalls.get(i));
    i++;
    while (i < toolCalls.size() && isConcurrencySafe(resolvedCalls.get(i)) == safe) i++;
    int segmentEnd = i;
    // safe 且段长>1 → 并行;否则串行
}
```

举例:模型一轮请求 `[Read A, Read B, Grep C, Write D, Read E]`
→ 切成三段:`[Read A, Read B, Grep C]`(安全,并行)→ `[Write D]`(串行)→ `[Read E]`(安全但段长 1,直接串行执行,不值得开线程池)。

**三个面试必讲的细节:**

1. **并发安全是"按输入"判定的,不是按工具类型写死的**(L219-227):`tool.isConcurrencySafe(typedInput)`——同一个工具可以对某些输入安全、对另一些不安全。简历里说"只读段"是简化说法,代码的真实语义是"并发安全段",判定权在每个工具自己手里。任何异常或无法解析输入 → 保守判为不安全。**方向永远是 fail-safe:拿不准就串行。**
2. **为什么保持段的连续性、不做全局重排?** 如果把所有安全调用挑出来先并行、再串行跑剩下的,执行顺序就和模型请求顺序不同了——而模型可能依赖顺序语义(先读后写)。切"连续段"意味着:**段与段之间的先后顺序严格保留,只在段内并行**。这是正确性优先于吞吐的取舍。
3. **独占工具(mustRunAlone,L80-88)**:有些工具(如进入 long-running 模式)要求单独成轮。如果模型把它和别的调用混在一轮里,**整批全部返回错误**——不是只拒绝它,也不是偷偷单独执行它。为什么?模型请求的是"同时执行"的语义,部分执行会让模型对世界状态的认知错乱;整批失败 + 明确错误信息,模型下一轮自己会拆开重试。确定性 > 聪明。

## 三、并发段:虚拟线程 + slot 回填(L122-181)

```java
ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();
Subscription killSub = cancellationToken.isCancellable()
        ? cancellationToken.onCancel(executor::shutdownNow)
        : () -> {};
try (killSub) {
    CompletionService<IndexedToolResult> completion = new ExecutorCompletionService<>(executor);
    // 提交时捕获 final int slot = k
    completion.submit(() -> new IndexedToolResult(slot, toolExecutor.execute(call, context)));
    // 取回时按 slot 归位,与完成先后无关
    results.set(completed.index(), completed.result());
} finally { executor.close(); }
```

**顺序保证的实现**:结果列表预分配为 `nCopies(size, null)`,每个任务提交时**捕获自己的 slot 索引**,完成后 `results.set(slot, result)` 归位。`CompletionService.take()` 是按完成先后取的(先完成先处理),但**放回去永远放在自己的 slot**——所以并行执行、顺序回填,两者不矛盾。这是这条简历 bullet 的技术核心,必须能白板画出来。

**为什么虚拟线程?** 工具执行几乎全是 IO 密集(读文件、跑子进程、网络请求),虚拟线程按任务创建零心智负担、阻塞成本极低;平台线程池要调大小、要管队列,对这种"一段最多十几个任务"的场景是过度设计。Java 21 的 `newVirtualThreadPerTaskExecutor` 正好一行搞定生命周期。

**kill-hook 的精细处理(L128-135 注释)**——这是全文件最"老练"的三行:

- 注册 `onCancel(executor::shutdownNow)`:用户取消时立刻打断执行中的工具;
- 用 `Subscription` + try-with-resources,**段一结束就注销钩子**——否则一个指向已关闭 executor 的回调会一直挂在 token 上,直到回合结束(内存与语义双重泄漏);
- 如果 token 不可取消(如 NEVER),**干脆不注册**——一个永远不会触发的钩子不是安全网,是死重。

**并发段的四条失败路径(L157-175)**全部收敛为同一个动作:`fillMissingConcurrentResults` 给所有还是 null 的 slot 填错误结果。已完成的保留真实结果,没完成的填错误——**没有任何 slot 会是 null**,配对完整性(模块 01 的不变量)在并发场景下依然成立。

**串行段的取消(L102-117)**:每个调用执行前查一次取消;一旦发现取消,当前位置之后的所有调用统一填"跳过"结果。注意有个特殊文案分支:如果取消原因是权限拒绝,消息是 *"Tool call skipped: previous permission request was denied"*——模型下一轮读到这句,知道是用户拒绝了权限,而不是系统故障,不会傻乎乎地原样重试。**给模型的错误信息也是 API 设计。**

## 四、ToolExecutor:七道关卡的执行管线(L109-294)

每个工具调用(无论并行还是串行)都要走完这条管线,**顺序本身就是设计**:

```
① 取消检查        已取消 → "skipped" 结果
② 工具解析        unknown tool → per-tool 失败(不是回合终止!)
③ 访问边界        本轮模型请求里没暴露的工具 → 拒绝(权威检查在这,orchestrator 的预检查只是优化)
④ PreToolUse Hook Hook 可以拒绝,也可以改写输入(effectiveInput)
⑤ Schema 校验     JSON Schema 验证 effectiveInput
⑥ Plan 模式门     计划模式下只放行只读工具
⑦ 权限门          PermissionGate.check → 可能弹框问用户
─────────────────
   输入强转为类型化对象 → tool.execute() → 记录证据/事件 → PostToolUse Hook
```

**四个高含金量追问点:**

1. **为什么 unknown tool 不终止回合?**(L130-147 注释写得非常好,建议原文读一遍)模型打错工具名是**可恢复的 per-tool 失败**——返回错误结果,模型下一轮改名重试即可。如果在这里发 `MetaEvent.Error`,那是**回合终止信号**(归 QueryEngine 用 FinishReason 管),会把同批其他工具的 UI 卡片全部清掉、让后续权限弹框无处渲染。**"per-tool 错误"和"回合终止错误"是两个严格分离的错误层级**——这个分层意识是高级感的来源。
2. **为什么 Hook 在 Schema 校验之前?** 因为 Hook 有权改写输入(L173-175),校验必须校验**改写后的 effectiveInput**——顺序反了就会出现"校验通过的输入和实际执行的输入不是同一个"的漏洞。
3. **为什么访问检查在 orchestrator 和 executor 各做一次?**(L149-153 注释)orchestrator 的预检查只为跳过无谓的输入强转/并发分类,是**优化**;executor 的检查才是**权威边界**——它绑定"本轮模型请求实际携带的工具声明",请求发出后才加载的工具,本轮不可调用,下一轮(重建 visibleTools 后)才行。双重检查不是冗余,是"优化层可以撒谎,权威层永不撒谎"。
4. **typedInput 的缓存与失效(L221-247)**:解析阶段把输入强转结果缓存进 `ResolvedToolCall`,但复用前要检查 `inputSnapshot.equals(effectiveInput)`——**如果 Hook 改写了输入,缓存立刻失效、重新强转**。快照用的是 `deepCopy()`。这是一个典型的"缓存 + 变更检测"微型案例,展示了对正确性的偏执。

另一个小而亮的点:`CURRENT_TOOL_USE_ID` ThreadLocal(L44)——权限弹框渲染时需要知道"是哪个工具调用在要权限",通过 ThreadLocal 传递,虚拟线程下每个任务天然隔离。

## 五、面试官追问预案

**Q1:你说读并行写串行——如果模型一轮请求 [读A, 写B, 读C],实际怎么执行?**
参考:切成三个连续段 [读A][写B][读C],全部串行(每段长度为 1,并行无意义)。只有**连续的**多个安全调用才会并行,例如 [读A, 读C, 写B] 会变成 [读A‖读C] → [写B]。段间顺序严格保留,不做全局重排——因为模型可能依赖请求顺序的语义。

**Q2:并行执行,怎么保证结果顺序和模型请求一致?**
参考:结果列表预分配,每个任务提交时捕获自己的 slot 索引,完成后 set 回自己的 slot;CompletionService 按完成先后取,但归位按 slot。执行乱序、回填有序。

**Q3:并行段跑到一半用户取消了,会发生什么?**
参考:取消钩子触发 `executor.shutdownNow()` 打断执行中的任务;已完成的 slot 保留真实结果,未完成的由 `fillMissingConcurrentResults` 填错误结果,后续段全部填"跳过"。所有 slot 非空 → tool_use/tool_result 配对完整 → 会话可续聊。

**Q4:为什么用虚拟线程而不是固定线程池?**
参考:工具执行是 IO 密集、批量小(一段最多十几个)、生命周期短(段结束即销毁)。虚拟线程按任务创建、阻塞廉价、不需要容量调优;`newVirtualThreadPerTaskExecutor` 一行管理生命周期。平台线程池的队列/容量/拒绝策略在这个场景全是不需要回答的问题。

**Q5:模型请求了一个不存在的工具名,你的系统怎么反应?**
参考:返回 per-tool 错误结果("unknown tool"),模型下一轮自行纠正。关键是**不能**发回合终止信号——错误分两个层级,per-tool 可恢复错误归 ToolExecutor,回合终止错误归 QueryEngine 的 FinishReason。层级混淆会导致同批其他工具被误杀。

**Q6:权限弹框用户点了拒绝,同一轮里排在后面的工具怎么办?**
参考:权限拒绝会触发取消(REASON_PERMISSION_DENIED),后续调用统一回填"skipped: previous permission request was denied"。文案是刻意区分的——让模型知道是用户拒绝而非系统故障,避免模型盲目重试。

**Q7(压力题):你这个切段算法,最坏情况下并行度是多少?值得吗?**
参考:最坏情况是安全/不安全交替出现(如 读写读写),所有段长度为 1,完全退化为串行——但这正是正确性要求的下界,不是缺陷。实际负载中模型倾向于批量发同类调用(如一次读五个文件),并行收益集中在这类真实场景。没有为最坏情况优化,因为最坏情况的串行就是正确答案。
