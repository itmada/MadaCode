# 模块 11 · 权限系统（补盲）

> 源码位置：`permission/` 包（2094 行）。核心：`DefaultPermissionGate`（175 行）+ 8 条 `PermissionRule` + `JLineApprovalPrompt`（300 行）+ `FilesystemScope`（407 行，包内最大）

## 一、30 秒电梯陈述（背下来）

> "权限决策是**三级流水线**：先过**规则链**——8 条规则按 PermissionLayer 排序逐条评估，任何一条给出结论（允许/拒绝）就短路返回，规则覆盖 bash 危险命令检测、plan 模式只读约束、文件系统作用域、权限姿态等；规则链全部弃权，查**会话记忆**——用户之前对同样的工具输入选过'本会话允许'，就自动放行；还没结论，才走**交互弹框**问用户，用户可以选允许一次、本会话允许、拒绝。每个决策不管来自哪一级，都带着层级和来源打**审计事件**——事后能回答'这个操作是谁批的、依据什么规则'。"

## 二、三级决策流水线（check 方法，L100-133）

```
① 规则链（8 条，按 PermissionLayer 排序）
   ├─ 任何规则返回 Optional.of(decision) → 短路，直接采纳
   └─ 全部返回 Optional.empty()（弃权）→ 进入下一级
② 会话记忆
   ├─ approvalKey = 工具名 + approvalSignature(input)
   └─ 命中 sessionApprovedInputs 集合 → 自动放行（来源标 session_memory）
③ 交互弹框（UserApprovalPrompt.requestApproval）
   ├─ ALLOW_SESSION → 放行 + 把 approvalKey 记入会话记忆
   ├─ ALLOW_ONCE   → 放行（不记忆）
   └─ DENY         → 拒绝（"User denied permission"）
```

**三个可讲细节：**

1. **规则弃权语义**：规则返回 `Optional<PermissionDecision>`——`empty` 表示"这事不归我管"，不是"我同意"。8 条规则大多只对特定工具/特定场景发言，比如 PlanModePermissionRule 只在 plan 模式下对写工具说"拒绝"，其他时候一律弃权。**弃权链 + 短路**是职责链模式的干净用法。
2. **规则顺序不靠调用方**（L55-57 + 类注释）：构造时按 `PermissionRule::layer` 排序——每条规则自己声明属于哪一层，gate 按层级结构排，而不是依赖调用方传列表的顺序。"跨层优先级是结构性的，不是约定性的"——把顺序这种易碎的隐式契约变成显式声明。
3. **会话记忆的 key 设计**：`工具名 + approvalSignature(input)`——签名由**工具自己**定义（Tool 接口方法），不是整个 input 的原文。为什么？比如 bash 工具可以决定"同一条命令"算同一签名，而忽略无关参数差异；文件写入可以按路径签名。**记忆的粒度是工具级知识，gate 不越俎代庖。**

## 三、8 条规则一览（不用背全，记住分类）

| 规则 | 管什么 |
|------|--------|
| `BashSafetyPermissionRule` | bash 命令安全检测（危险命令拦截/升级审批）|
| `PlanModePermissionRule` | plan 模式下拒绝写操作（模块 02 第六关的实现处）|
| `LongRunningTaskStatePermissionRule` / `LongRunningWorkspacePermissionRule` | long-running 任务状态与工作区约束 |
| `ToolSearchPermissionRule` / `SessionProgressPermissionRule` | 特定工具的放行规则 |
| `FilesystemReadPermissionRule(trustedRoots)` | 文件读取的信任根约束——受信目录内自动放行 |
| `PosturePermissionRule` | 权限姿态（DEFAULT/BYPASS 等 permissionMode）的兜底决策 |

分类记法：**安全类**（bash 安全、文件系统作用域）、**模式类**（plan 模式、long-running 状态）、**姿态类**（permissionMode 兜底）。`FilesystemScope`（407 行，包内最大类）负责路径归一化和作用域判定——防路径穿越（`../`）、符号链接逃逸这类把戏。

## 四、审计（recordDecision，L151-167）

每个决策发两路：`diagnosticEvents.permissionDecision`（诊断日志）+ `AuditEvent.permissionDecision`（审计事件），携带：工具名、允许/拒绝、理由、**决策层级**、**决策来源**（规则名/session_memory/user_prompt）、用户等待毫秒数、输入截断 500 字符。

> 面试一句话："任何一个工具执行，事后都能回答'是谁批的'——是哪条规则自动批的、还是会话记忆、还是用户手点的，等了用户多久。Agent 的自主性越强，审计链就越重要。"

## 五、与已学模块的连接（考试可能串联）

- **模块 02 第七关**：`ToolExecutor` 的 `permissionGate.check(tool, effectiveInput, context)` 就是进入这条三级流水线。注意传的是 **effectiveInput**（Hook 改写后的），审批的是真正要执行的输入。
- **模块 05 共享 gate**：子 Agent 复用同一个 gate 实例 → 同一份 sessionApprovedInputs（父批过的签名子也免弹框）、同一个 prompt 出口（弹框在用户终端）。
- **模块 03 权限拒绝取消**：用户在弹框选 DENY → 工具返回失败 → 触发 REASON_PERMISSION_DENIED 取消 → PERMISSION_CANCELLED 终态。弹框的三个选项里只有 DENY 走这条链。
- **模块 06 BYPASS 模式**：`PosturePermissionRule` 在 BYPASS 姿态下自动放行——这就是 long-running 无人值守能跑起来的原因（危险操作不弹框），也是为什么子 Agent 严格继承 permissionMode 那么重要。

## 六、追问预案（口语版）

**Q1：你的权限系统怎么设计的？**
> 电梯陈述。结尾补："设计上核心是三层的职责分离——规则管'确定的事'，记忆管'用户说过的事'，弹框管'拿不准的事'。"

**Q2：为什么规则返回 Optional 而不是 boolean？**
> "boolean 只有允许/拒绝两态，表达不了'不归我管'。三态（允许/拒绝/弃权）才能做职责链：每条规则只对自己的领域发言，弃权就交给下一条。要是用 boolean，每条规则都被迫对所有工具表态，规则之间的耦合会爆炸。"

**Q3：'本会话允许'怎么防止被滥用？比如批了 `ls` 结果放行了 `rm -rf`？**
> "记忆的 key 是工具名加 approvalSignature——签名由工具自己定义，bash 工具的签名包含命令本身，`ls` 和 `rm -rf` 是两个签名，批前者不会放行后者。签名粒度是工具级知识，每个工具自己决定'什么算同一个操作'。"

**Q4：BYPASS 模式下所有操作都放行，安全吗？**
> "BYPASS 是用户显式选择的姿态，语义就是'我信任这次会话'。但它不是完全裸奔——规则链在弹框**之前**，bash 安全规则、文件系统作用域这些结构性约束照常生效，BYPASS 跳过的只是'问用户'这一步。另外派生子 Agent 严格继承姿态、不能自提权，审计事件照常记录。"

**Q5：为什么审计要记录用户等待时长？**
> "它是权限体验的核心指标——弹框太频繁用户会烦到直接开 BYPASS，等于安全机制把用户推向了不安全。看等待时长的分布能知道哪类操作该加自动放行规则、哪类签名粒度设计得太细。安全机制的可用性决定它的实际安全性。"
